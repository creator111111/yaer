## 1. 需求摘要（任务卡 → 工程语义）

### 1.1 场景与命名

策划在树屋下布置 **两个 Trigger 体积**，本文统一记为 **Trigger-0**、**Trigger-1**（与场景 / 代码下标一致）。原任务卡「先经过 A 再经过 B」的编号若与场景物体名不一致，**以策划表为准做 0/1 映射**，避免与文档 §3 决策表错位。

**目标物体**：**「DepthZone&Colliders」**（父节点），对其 **`SetActive(true/false)`** 或等价启用策略仍由 **单一门控组件** 写入（见 §4）。

### 1.2 原任务卡语义的保留关系（备案）

| 原任务卡表述（方向性） | 与 §1.3 的关系 |
|------------------------|----------------|
| 沿行进方向「先 1 后 2」→ 开 | 在 **宽脚点** 前提下，**不再**用「离散两次 Enter 的先后顺序」作为唯一依据，改为 **§1.3 双接触 + 先碰 + 收尾** 规则表 |
| 「先 2 再 1」→ 关 | 同上，由 §1.3 中 **先碰 1 且双接触后以 0 收尾 → 关** 等条目覆盖 |

**结论**：**以 §1.3 为施工与验收主规格**；原任务卡作意图备案。

### 1.3 【新增主规格】宽 PlayerFoot：双接触时刻 + 先碰谁 + 收尾谁

#### 1.3.1 动机（为何改规则）

玩家 **PlayerFoot** 碰撞体在横向上 **较长**（Prefab 常见为宽胶囊），极易 **同时与 Trigger-0、Trigger-1 重叠**。若仍依赖「两次 `OnTriggerEnter2D` 谁先派发」判定先后，会引入 **同帧顺序不确定** 与 **伪先后**，与策划直觉不符。

因此：**激活 / 取消的决策时机** 改为围绕 **「曾出现 0 与 1 同时与玩家脚点接触」** 这一段过程；在 **已知先碰的是 0 还是 1** 的前提下，根据 **从双接触状态脱出后、脚点仍与哪一侧 Trigger 保持接触（收尾）** 决定 **开 / 关 / 不变**。

#### 1.3.2 术语（便于实现与验收对齐）

| 术语 | 含义 |
|------|------|
| **先碰 X** | 在本轮逻辑关心的时间窗内，**首次**出现「仅与 Trigger-X 接触、尚未与另一侧同时接触」的时刻；若因脚点过宽 **从未出现单侧仅 0 或仅 1**，则见 §7 **同帧双进** 补规则。 |
| **同时有 01** | 某一时刻 **Trigger-0 与 Trigger-1 均与 PlayerFoot 重叠**（两路 `OnTriggerEnter2D` 均已对同一玩家成立，或等价布尔 `in0 && in1`）。 |
| **最后是 X** | **在已经历「同时有 01」之后**，玩家脚点从「双接触」变为 **仅与 Trigger-X 接触**（仍压在 X 内、已脱离另一侧）的 **收尾侧**；用于查表。未出现「同时 01」的路径见下表「无 01」行。 |

#### 1.3.3 决策表（主规格）

下表中 **「不变」** 表示：**不调用** `SetActive` 翻转目标当前状态（门控不强行改开关）。

| 先碰 | 是否经历「同时 01」 | 收尾（双接触之后的单侧） | 对 DepthZone&Colliders 的结果 |
|------|----------------------|---------------------------|-------------------------------|
| **0** | 是 | **最后是 1** | **激活**（打开） |
| **0** | 是 | **最后是 0** | **关闭**（取消） |
| **0** | 否（全程未与 1 同时、也未单独进 1） | **只有 0**（未碰到 1） | **不变** |
| **1** | 是 | **最后是 0** | **关闭** |
| **1** | 是 | **最后是 1** | **保持打开**（见下方注） |
| **1** | 否 | **只有 1**（未碰到 0） | **不变** |

**注 —「保持打开」**：语义为 **本路径不得执行关闭**；若当前目标为 **Inactive**，是否须 **`SetActive(true)`** 与「仅不关闭」等价，**须策划二选一**（见 §7）。推荐默认：**仅当当前已为 Active 时保持**；若当前为 Inactive 则 **不变**（与「先碰 1 无 0」一致、表内逻辑更统一）。

**工程解读**（与 `VillagePlayerDepthZone` 的关系不变）：

- **「DepthZone&Colliders」** 多为父节点，子级挂 **DepthZone** 与 **Collider**；整包开关避免漏关。
- 门控与 **`VillagePlayerDepthZone` 改玩家 Sorting** 正交；父物体 `SetActive(false)` 时子 Zone 会 `OnDisable` 并走已有注销逻辑（见 §4）。

## 3. 推荐架构（满足 MASTER_PROMPT「最小改动、禁堆 Update 业务」）

### 3.1 组件形态（建议新建，类名由施工 PR 定）

**推荐**：场景侧 **一个** 协调器（示意名 **`VillageTreehouseDepthZoneGate`**），职责：

| 职责 | 说明 |
|------|------|
| **两路 Trigger 回调** | 子物体各挂 Trigger + **薄转发**（或单物体两 `Collider2D` + 引用区分），向协调器上报 **Enter/Exit** 的 **索引 0/1** 与 **`Collider2D other`**。 |
| **每玩家脚点会话状态** | 对合法 `PlayerLogic`（或唯一玩家）维护 **`in0`/`in1`**、**`firstTouched`**（`None`/`0`/`1`）、**`hadBoth`**（是否已出现过同时 01）、以及 **「双接触刚结束后的收尾侧」** 的判定用缓存。逻辑仅在 **Enter/Exit** 内更新，**禁止**在 `Update` 里做业务判定。 |
| **单一写口** | 仅此处对 **`DepthZone&Colliders`** 调用 `SetActive`。 |

### 3.2 状态机与事件（与 §1.3 对齐）

**布尔与边**（实现时可换名，语义须一致）：

- `in0`、`in1`：当前帧语义下 PlayerFoot 是否分别与各 Trigger 重叠（由 Enter/Exit 维护）。
- **边 A**：`!(in0 && in1)` → `(in0 && in1)`：进入 **双接触**；若此时 **`firstTouched == None`**，应用 §7 **同帧双进** 规则补全「先碰」。
- **边 B**：`(in0 && in1)` → 仅一侧为真（`xor`）：**双接触结束**，根据 **先碰** 与 **收尾侧（仅剩 0 或仅剩 1）** 查 **§1.3.3 表**，执行 **激活 / 关闭 / 不变**。
- **边 C**：从未进入双接触，且仅单侧 Enter/Exit 游荡：**不执行**表中「激活/关闭」行（对应「先碰 0 无 1」「先碰 1 无 0」→ **不变**）。

**`firstTouched` 的重置策略（建议）**：在 **边 B 执行完查表动作后** 将 `firstTouched` 置 `None`、`hadBoth` 置 `false`，以便下一轮穿行重新积累；若策划要求 **跨多次双接触记忆**，改为显式状态并在 §7 文档化。

### 3.3 Trigger 实现方式（两选一）

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A（推荐）** | 两子物体 + 转发 `NotifyEnter(0|1)` / `NotifyExit(0|1)` | 消息边界清晰 | 多薄脚本 |
| **B** | 单物体两 `Collider2D`，回调里 `==` 比较引用 | 节点少 | 易与其它 Collider 混淆 |

### 3.4 检测层与玩家引用

- 与 `VillagePlayerDepthZone` 一致：**`PlayerFoot` 层** + `GetComponentInParent<PlayerLogic>()`。
- **替代方案**：Tag 判定须在注释与验收表中写明与脚点文档的差异。

### 3.5 实现侧伪代码（供【施工员】对齐，非强制语言）

下列伪代码强调 **仅在 Exit 导致的「双变单」时结算**，避免在 `Update` 轮询：

```
// 维护 in0, in1, firstTouched ∈ {None,0,1}, hadBoth

OnEnter(i):  // i ∈ {0,1}
  if (!IsPlayerFoot(other)) return
  if (!in0 && !in1) firstTouched = i   // 从「双都不在」进入单侧：记下先碰（若从双进单见 §7）
  in[i] = true
  if (in0 && in1) hadBoth = true

OnExit(i):
  if (!IsPlayerFoot(other)) return
  bool wasBoth = in0 && in1
  in[i] = false
  if (wasBoth && (in0 ^ in1))   // 刚从双接触变为恰好一侧
     last = in0 ? 0 : 1
     ApplyTable(firstTouched, hadBoth, last)  // 对应 §1.3.3
     ResetSessionFlags()   // 或按策划跨周期保留
```

**须在代码注释中写明**：为何在 **`wasBoth && 单侧残留`** 时结算（宽脚点 + 与策划表一致）。

## 4. 风险与与现有系统的协作

| 风险 | 说明 | 缓解 |
|------|------|------|
| **同帧内 in0/in1 同时变 true** | 「先碰」在纯离散事件下 **不可观测** | §7：约定 **tie-break**（脚点中心到两 Trigger 最近点距离、或按世界 X/Y 与策划箭头一致、或固定优先级并写入场景 README） |
| **从双接触直接到双都不接触**（无「单侧收尾」） | 表中以「最后是 0/1」为键；**双出**未定义 | §7：约定为 **不变** 或 **按上一帧单侧近似**；须在门控内注释 |
| **关掉父物体 `DepthZone&Colliders` 时** | 子 `VillagePlayerDepthZone` → `OnDisable` → `NotifyUnregisterAll()` | 无需改 Zone 脚本；验关闭后排序无泄漏 |
| **双写 active** | 仅门控写目标 `SetActive` | 与 MASTER 一致 |
