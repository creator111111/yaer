## 1. 结论摘要（给施工员）

**主因（高置信）**：在 **`PlayerLocomotionMode.Village2_5D` 且使用 Combat 地面 Run 状态机**（`CombatRunState`）时，`Update` 中有一段**每帧**在「纵深仍有意图」但「`HasMoveInput()` 为假」时调用 **`PlayerMoveComponent.StopMoveInX()`**，把横向目标速度/刚体水平速度**持续清零**。  
纵深意图来自 **`TownPlayerLocomotion.HasVillageDepthMoveForHomeStateMachine()`**（内部优先 **`Input.GetAxisRaw("Vertical")`**），与 **`PlayerInputComponent` 的指令队列 `curPlayerAllCmds`** **不是同一套数据源**。  
而 **`HasMoveInput()` 仅判断队列「队首」是否为 Left/Right**，无法表达「仍按着 A/D 但队首被其它指令占位 / 尚未入队」等情况 → 与纵深意图组合后，易出现**横向被每帧清掉**，玩家体感为「卡横移」，通过**再次 KeyDown 方向键**刷新队列或队首后恢复 —— 与策划描述高度一致。

**次要/放大因素（中置信）**：`ParseMoveCmd` 在 **`PlayerMoveComponent.IsMoveUp/IsMoveDown`** 时整段提前 `return`，本帧不再走 `MoveRight/MoveLeft` 的刷新路径；若与上条叠加，会进一步造成「有输入但不刷新横向」的窗口。  
**物理与写回顺序（低～中置信）**：`TownPlayerLocomotion.WriteRootTransformWithAuthoritativeDepthY` 从当前 **`Rigidbody2D.velocity.x`** 取值写回 `(v.x, 0)`；若与 `MoveComponent.OnFixedUpdate`、Physics2D 步进顺序叠加，在**贴障碍的几何姿态**下可能短暂读到 `v.x≈0`（需在目标机上开执行顺序与帧日志验证）。

**与纵深障碍夹紧本身的关系**：`TownPlayerLocomotion.ApplyVillageWalkObstacleDepthClamp` 在阻挡时会把 **`depthVelocity` 置 0** 并夹紧权威 Y；**不会直接写 `moveSpeedX`**。现象上「撞纵墙后横移异常」更容易落在 **CombatRunState + 输入队列语义** 这一层，而不是单纯 Cast 夹紧算法。

**「无法定位」时的阅读指引**：若团队在「输入是否连续判定」与「位置判定是否不准」之间摇摆，**以正文 §2 表格 + §2.2 三步验证**为裁决顺序；静态代码结论为 **Combat 轨门控错杀横向速度（§2.1-B）为主因**，WalkArea / Cast 单独构成主因的证据不足。

## 2. 定位分歧拆解：究竟是「输入不连续」还是「位置不准」？

团队内部若出现「不知道是按键没被连续判定」还是「判定/写回位置导致抖卡」两类怀疑，可按下表**对照代码事实**归纳根因归属。

### 2.1 一句话结论

| 怀疑方向 | 是否为主因（本仓库静态结论） | 依据摘要 |
|----------|------------------------------|----------|
| **A. 横移输入硬件/帧率上不连续**（未每帧读到 A/D） | **基本否** | 长按类指令在 **`PlayerInputComponent.OnUpdate` → `ParsePlayerCmd` → `ParseMoveCmd`** 路径下**每帧**处理队首；`Left` / `Right` 属于 **`longPressCmd`**，不会在松开前被 `Remove`（除非 `KeyUp` 或清空队列）。问题不在「有没有连帧采样」，而在**队首是不是 Left/Right**、以及 **Combat `StopMoveInX` 是否与「纵深意图」错配**。 |
| **B. 「有横移」的语义只看队首 `HasMoveInput()`** | **是（Combat 轨主因）** | `HasMoveInput()` 仅比较 **`curPlayerAllCmds[0]`**；与 **`HasVillageExploreDepthMoveIntent()`（`GetAxisRaw("Vertical")`）** 数据源不一致 → 易误判「无横移」→ **`CombatRunState` 每帧清 X**。这与「要重按方向才恢复」（刷新队首或触发新的 `ParseMoveCmd` 条件）高度吻合。 |
| **C. WalkArea 多边形逐帧把 X 拽回导致「位置战」** | **通常为次因/场景依赖** | `ApplyVillageWalkPolygonPostCorrection` **仅当** `OverlapPoint(刚体参考 XY)` 为假时才修正位置；角色在合法多边形**内部顶纵墙**时，多数帧 **不会**因 WalkArea 单独造成横向零点重置。若策划把多边形切得极薄或参考点抖动出界，才需怀疑此项（可开 `acceptanceDebugLog` 与场景 Gizmo 对照）。 |
| **D. 纵深障碍 Cast「位置不准」拖死横移** | **否（机制上不对 X 下刀）** | `ApplyVillageWalkObstacleDepthClamp` 只改 **`_villageWorldY`** / **`depthVelocity`**；不写 **`moveSpeedX`**。手感上若误以为是「碰撞判不准」，应先排除 `CombatRunState` 清 X。 |
| **E. FixedUpdate 内 Town 与 Move 顺序导致 `velocity.x` 误读** | **低～中置信、用作补强验证** | `Player.prefab` 中二者 **`priority` 均为 0**；`ComponentSystemMono.OnFixedUpdate` 按 **`componentsList` 序列**依次调用子组件 `OnFixedUpdate`。根物体上该列表中 **`PlayerMoveComponent`（fileID `8492089656308942601`）排在 `TownPlayerLocomotion`（`7600110044002200003`）之前**，与 `Components` 子物体上 Move 的 **`m_RootOrder: 3`**、Town 的 **`11`** 一致 → **每物理帧先由 Move 写入 `rg.velocity`，再由 Town 读 `v.x` 写回 `(v.x, 0)`**。该顺序**本身**不解释「撞纵墙后必卡横移」；若 **`v.x` 已在 `Update` 被 `StopMoveInX` 清零**，则会与 B 叠加表现为「横移起不来」。 |

### 2.2 若仍无法在组内达成共识：最小验证协议（不改架构前提）

1. **只加日志**（标签建议 `[VillageMoveDebug]`）：在 **`CombatRunState.Update`** 打印 `HasMoveInput`、`HasVillageExploreDepthMoveIntent`、队首指令、`moveComponent.moveSpeedX`、`rb.velocity.x`。若出现「**物理上按住 A/D**（或队列中仍存在 Left/Right）但 **`HasMoveInput==false`** 且纵深意图为 true」与 **`StopMoveInX` 连续帧**，即可**将主因钉死在 §2.1-B（队首语义 + Combat 清 X）**，而不是「位置/采样不连续」。  
2. **同机对照**：换装 **Home 控制器** 重复顶墙 + 斜向输入；若问题显著减弱或消失，进一步排除「纯 WalkArea / 纯 Cast」为全局主因。  
3. **关障碍夹紧**：仅关 **`TownPlayerLocomotion.enableVillageDepthObstacleClamp`**；若横移迟滞**几乎不变**，说明瓶颈不在 Cast 精度而在 **Combat 门控 + 队列语义**。

### 2.3 与「卡顿」词义的对应

- **因 B（门控错杀）导致的「卡」**：每帧逻辑清零横向速度，表现为**持续无位移**，直到输入状态机条件变化（重按、改队首或队列被 `ParseMoveCmd` 重新走通）。  
- **因 C/E（几何/顺序）导致的「卡」**：更偏**抖动、瞬移、贴边来回**；需依赖 `OverlapPoint`、修正位移量或物理后 `velocity` 波形才能成立。

## 3. 逻辑溯源（按真实调用链）

### 3.1 纵深障碍（几何夹紧）

- **入口**：`TownPlayerLocomotion.OnFixedUpdate` → `ApplyVillageWalkObstacleDepthClamp` →（命中）`_villageWorldY` 修正 + **`depthVelocity = 0`**。  
- **代码位置**：`Assets/Scripts/Game/GameRuntime/Entities/Player/Components/TownPlayerLocomotion.cs`（`ApplyVillageWalkObstacleDepthClamp` 内多处 `depthVelocity = 0f`）。  
- **文档对照**：《村庄探索_场景遮挡与Walk区内障碍碰撞》§4.3 — W/S 由脚本写权威 Y，必须在写回前 Cast/夹紧。

### 3.2 纵深「仍在移动/有意图」判定（与输入队列解耦）

- **入口**：`BasePlayerState.HasVillageExploreDepthMoveIntent()` → `TownPlayerLocomotion.HasVillageDepthMoveForHomeStateMachine()`。  
- **语义**：只要 **`Input.GetAxisRaw("Vertical")` 超过阈值**即返回 `true`，**不依赖** `curPlayerAllCmds` 里是否有 W/S 映射的指令。惯性段才看 `depthVelocity` 与 `enabled`。  
- **代码位置**：同上文件 `HasVillageDepthMoveForHomeStateMachine`。

### 3.3 「是否有横移输入」判定（仅看队首）

- **入口**：`PlayerInputComponent.HasMoveInput()`。  
- **语义**：构造 `Left/Right` 列表，判断 **`GetPlayerCurInputCmd()`（即 `curPlayerAllCmds[0]`）** 是否为左/右；**不扫描**整个队列，也**不读取** `Horizontal` 轴。  
- **代码位置**：`Assets/Scripts/Game/GameRuntime/Entities/Player/Components/PlayerInputComponent.cs`。

### 3.4 Combat 跑态下「清横向」每帧门控（关键）

- **入口**：`CombatRunState.Update`。  
- **条件**（与文档注释一致，原文意图是避免纵深层与横移速度叠加）：  
  `LocomotionMode == Village2_5D && !inputComponent.HasMoveInput() && HasVillageExploreDepthMoveIntent()`  
  → **`moveComponent.StopMoveInX()`**。  
- **效果**：`StopMoveInX` 将 **`MoveComponent.Velocity.x = 0`** 且 **`Rigidbody2D.velocity` 的 x 置 0**（见 `MoveComponent.StopMoveInX`）。  
- **代码位置**：  
  - `Assets/Scripts/Game/GameRuntime/Entities/Player/Components/CsAnimator/Combat/State/Ground/CombatRunState.cs`（`Update` 内约 60–66 行）；  
  - `Assets/Scripts/Game/GameRuntime/Entities/Component/Move/MoveComponent.cs`（`StopMoveInX`）。

### 3.5 Home 走态（对照）

- **`HomeWalkState`**：`Update` 仅在「无 `HasMoveInput()` 且无纵深意图」时退回 Idle/Bink；**没有**与 `CombatRunState` 对称的「纵深意图时每帧 `StopMoveInX`」逻辑。  
- **代码位置**：`Assets/Scripts/Game/GameRuntime/Entities/Player/Components/CsAnimator/Home/HomeWalkState.cs`。

### 3.6 与 `02_SYSTEM_SPEC` 的对应关系

- 规范已写明：村庄 W/S 在 **Combat** 轨由 `CombatIdleState` / `CombatRunState` 与 `TownPlayerLocomotion` 协同；`CombatRunState` 中「松横移后清 X」是为避免与纵深写 Y 叠移（见 `CombatRunState` 注释）。  
- **当前副作用**：该门控使用的 **`HasMoveInput()` 语义过窄**（队首唯一），与 **`HasVillageExploreDepthMoveIntent()`（竖轴 Raw）** 组合后，在「撞墙后仍按住 W/S」的常见操作下，**极易误判为「无横移」** → 每帧清 X。

## 4. 典型复现路径（便于验收对齐）

下列路径**不要求**玩家松开 W/S；重点观察 **Combat 控制器**（`RuntimeAnimatorController` 名称含 `Combat` 的换装）：

1. **纯纵深远进入 Run**：只按 W/S 进入 `CombatRunState`（`Enter` 内 `villageDepthOnly` 分支可能未 `SetRunSpeed`），再按下并保持 A/D；若队首曾被其它 `KeyDown` 插入非 Left/Right 指令，观察是否出现数帧～持续的横移「被抽空」。  
2. **先 AD 再顶纵墙**：保持 A/D 与 W/S；纵深被 `VillageWalkObstacle` Cast 截断后 `depthVelocity=0`，**竖轴仍按住**；若此时 `HasMoveInput()` 因队首或队列状态为假，应能稳定看到 `StopMoveInX` 生效。  
3. **换装对照**：同一操作在 **Home 控制器**（`HomeWalkState`）下是否明显减轻（若减轻，则佐证 Combat 分支为主因）。

**推荐日志（验收员）**：在 `CombatRunState.Update` 内临时加标签（如 `[VillageMoveDebug]`）打印：  
`HasMoveInput`、`HasVillageExploreDepthMoveIntent`、`curPlayerAllCmds` 前 3 项、`Velocity`、`rb.velocity` —— 与 `00_MASTER_PROMPT` 中验收员模式一致，**用完删除**。

## 5. 施工方向（最小改动原则；须施工员合入前评审）

> 下列为**方向**说明，避免在侦探文档中写死实现细节；具体 API 以仓库为准。

| 优先级 | 方向 | 说明 |
|--------|------|------|
| **P0** | 收紧 `CombatRunState` 中 `StopMoveInX` 触发条件 | 仅在「确认玩家**未**持有横向位移意图」时清 X。意图源建议与**真实按键/轴**对齐，而非仅 `curPlayerAllCmds[0]`。注意任务卡「不改编 `InputActions` 资产」与「在现有 C# 中读 `Input.GetAxisRaw("Horizontal")`」的边界由主程裁定。 |
| **P1** | 修正 `HasMoveInput()` 语义或新增专用查询 | 例如：在**不移除现有 API** 前提下增加 `HasHorizontalMoveCommandInQueue()`（扫描 `curPlayerAllCmds` 是否含 Left/Right），供村庄 Combat 专用；避免破坏其它依赖「队首即当前指令」的旧逻辑。 |
| **P2** | 复核 `FixedUpdate` / `WaitForFixedUpdate` 回调顺序 | `TownPlayerLocomotion` 的 `WriteRootTransformWithAuthoritativeDepthY` 与 `MoveComponent.MoveVelocity`、`PostPhysicsResyncDepthCoroutine` 与物理步的先后，必要时用 **Script Execution Order** 固定「横移写入 → 物理 → 纵深写回」的可预期顺序（与第三阶段执行说明 §8「物理顺序」一致）。 |

## 6. 替代方案（文档级）

| 方案 | 优点 | 风险 / 成本 |
|------|------|-------------|
| **A. 仅改 `CombatRunState` 门控** | 改动面极小，直击手感问题 | 需仔细定义「横向意图」，避免与纵深叠移回归 |
| **B. 统一用轴驱动村庄横移（大改）** | 语义与 `Vertical` 对称 | 与现有「指令队列 + 事件」架构冲突面大，违背第三阶段「不改输入系统」精神 |
| **C. 村庄强制 Home 控制器** | 绕开 CombatRun 特化逻辑 | 影响换装与战斗资源管线，属产品决策，非程序单点修复 |
