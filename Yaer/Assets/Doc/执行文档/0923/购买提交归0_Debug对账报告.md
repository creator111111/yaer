# 购买提交归 0 · Debug 对账报告

> 日期：2026-09-23  
> 性质：给产品/联调的 **Debug 说明**（配合 Console 过滤）  
> Unity：2020.3.48f1  
> 目的：说清「有 800 金、东西才几百，提交后数量为何变 0」

---

## ① 一句话

**变 0 多数不是因为钱不够，而是该道具背包已经装满（10/10），空位 = 0，可买上限被算成 0。**  
钱只决定「最多能买几件」；**空位为 0 时，再有钱上限也是 0。**

---

## ② 你怎么对账（Play 后看 Console）

1. 打开 Console，过滤：`[ShopBuyCommit]`
2. 购买 Tab 点一行，输入数量，失焦 / 回车 / 点别处（触发提交）
3. **每次提交必出一行**，例如：

```
[ShopBuyCommit] item=HpBall 输入数量=1 单价=200 金币=800 其它行占金=0 持有=10/10 空位stackRoom=0 钱够买afford=4 上限max=0 提交后数量=0 原因=背包已满(持有10/顶10)→空位0→上限0【不是没钱】
```

| 字段 | 含义 |
|------|------|
| 输入数量 | 你敲进去、提交前的数 |
| 单价 | 这一行买价（表/Bake，可能是 200 或你说的 400） |
| 金币 | 当前钱包（应和菜单 ~800 一致） |
| 其它行占金 | 其它购买行已经填的数量×价 |
| 持有 / 顶 | 背包里已有几个 / 每种最多几个（现网顶=10） |
| 空位 stackRoom | `10 − 持有`；**0 = 塞不进** |
| 钱够买 afford | `(金币−其它行占金) ÷ 单价` 向下取整 |
| 上限 max | `min(afford, 空位)` ← **真正用来钳数量的数** |
| 提交后数量 | 钳完写回框里的数 |
| 原因 | 人话：为何从输入变成提交后 |

另可过滤 `[ShopBuyMax]` / `[ShopDebug] 提交后数量调整` 作对照。

---

## ③ 用你的例子手算（800 金）

### 若单价 400（你说的「400 块的东西」）

```
钱够买 = 800 ÷ 400 = 2 件
若背包该道具已 10/10：空位 = 0
上限 max = min(2, 0) = 0
→ 输入 1 提交后 → 0
```

**不是**「800 不够付 400」——付得起，但**背包没空位再收一件**。

### 若单价 200（生命球现网常见表价）

```
钱够买 = 800 ÷ 200 = 4 件
持有 10 → 空位 0 → max = 0 → 同样提交归 0
```

### 什么时候不会归 0？

先把该道具用掉 / 调试减数量，使 **持有 &lt; 10**，例如持有 6：

```
空位 = 4
单价 400 → max = min(2, 4) = 2  → 输入 1 提交后留下 1
单价 200 → max = min(4, 4) = 4  → 输入 1～4 可留下
```

---

## ④ 和「钱不够」怎么区分

| Console「原因=」 | 含义 |
|------------------|------|
| `背包已满…【不是没钱】` | 有金；空位 0；**你现在最常见的情况** |
| `金币不够买1件` | 真的钱不够付 1 件 |
| `超过可买上限max=N` | 钱和空位都有，但你输超了，钳到 N（不会无故变 0） |
| `未调整(在上限内)` | 输入合法，提交后不变 |

---

## ⑤ 请你贴回的一行（方便继续查）

把 **同一次** 提交的 `[ShopBuyCommit]` 整行复制过来即可。若仍是：

- `金币=800`、`钱够买afford≥1`、`空位stackRoom=0`、`提交后数量=0`  

则计算按设计如此，下一步是 **腾空位再买**，不是改「读金公式」。

若出现 `金币=0` 或 `单价=0` 而菜单显示有钱，再查读档/行价——把那一行日志贴出即可。
