# 购买输入仍变 0 · 有金无法买 · 复验热修 · 架构溯源报告

> 日期：2026-09-23  
> 角色：架构侦探（诊断日志已挂；**未改**联合钳制公式 / Prefab / Database）  
> Unity：2020.3.48f1  
> 现象：有约 **800** 金，购买端输入**仍一律变 0**，无法购买（上一轮施工验收失败）  
> 场景：`Village_Shop` 购买 Tab · 生命球（`HpBall`，表价 **200**）  
> 提示词：`Assets/Doc/提示词/0923/购买输入仍变0_有金无法买_复验热修_架构侦探提示词.md`  
> 证据源：本机 `Editor.log`（`[MenuMoney]` / `[ShopDebug]`）+ 现网公式；并已在 `ResolveBuyMaxQuantity` 挂 `[ShopBuyMax]` 供施工验收再贴一行

---

## ① 结论一句话

**根因 = G2（堆叠空位 0），不是「读不到 800 金」。**  
`HpBall` 持有已满 `MaxStackPerItem=10` → `stackRoom=0` → `ResolveBuyMaxQuantity` 恒返回 **0** → `ClampQuantityToCap` 把任意键入写回 **0**。菜单 800 金与商店读金同源，G1 证伪。

上一轮只修了清空时序（Z2）与 PointerClick（R1）/ 单价口径，**从未钉死 max=0 的分解字段**，故「声称修好」后现网仍复现——本票按复验失败热修。

---

## ② 强制实测表（Play / Editor.log）

| 字段 | 实测 | 证据 |
|------|------|------|
| MenuMoney gold | **800** | `[MenuMoney] SetNumber display=800 (archive gold=800)`（日志约 L3748888、L9403430） |
| Shop 读金路径 | 与菜单**同一** `QuestManager.GetPlayerGoldData()` | `MenuFormLogic.RefreshMoneyFromArchive` ↔ `ResolveBuyMaxQuantity` |
| price（生命球） | **200** | `MainItemDatabase.asset` HpBall `buyPrice: 200`；Bake 行价同源 |
| held / stackRoom | **held=10 / stackRoom=0** | `[ShopDebug] 背包将超堆叠上限：HpBall 持有 10 + 购买 11 > 10`（约 L9811258 起多次） |
| otherCost | **0**（单行试买、无其它行占金时） | 公式侧；非主因 |
| max | **0** | `min(affordByGold, stackRoom)=min(⌊800/200⌋, 0)=0` |
| 按 1 后 TMP/DigitStrip | **变 0** | `TryClamp` → `ClampQuantityToCap(1, 0)` → 写回 0（与产品描述一致） |

### 等价 `[ShopBuyMax]` 一行（按上表代入；代码已能打出）

```
[ShopBuyMax] item=HpBall gold=800 price=200 held=10 stackRoom=0 otherCost=0 max=0 bypassGoldCheck=0
```

施工验收：清空/消耗生命球使 `held<10` 后，须贴到 `max≥1` 的实打日志（例 `held=0 stackRoom=10 max=4`）。

## ③ 假说裁定

| ID | 假说 | 裁定 |
|----|------|------|
| **G1** | `GetPlayerGoldData` null / gold=0，与菜单不一致 | **证伪**。菜单已打出 archive gold=800；商店与菜单走同一 `QuestManager` 门面 |
| **G2** | `stackRoom==0`（满堆叠）→ max 恒 0，与金币无关 | **主因坐实**。`ShopDebug` 明确 `HpBall 持有 10`；`MaxStackPerItem=10` |
| **G3** | `price≤0` | **证伪**。Database / Bake 买价 200；上轮已统一 `ResolveBuyUnitPrice` |
| **G4** | otherRowsCost 吃光 remaining | **非主因**。单行生命球试买时 otherCost 不影响；满堆叠已足够解释 max=0 |
| **C1** | max>0 仍被写 0 | **证伪（本档）**。本档 max 已为 0，Pipeline 写 0 是正确钳制结果 |

### 为何「有 800 还是买不了」

大白话：钱够买 4 个，但背包里生命球已经 **10/10 装满**，商店公式不允许再买进。输入框不是「坏了」，是上限算出来就是 0，所以你敲什么都变成 0。上一轮修的是「怎么清空/再点」，**没碰「满堆叠时 max=0」这件事**，所以验收必然失败。

```
键入 1
  → TryClampQuantityToBusinessMax
       max = ResolveBuyMaxQuantity
            held=10 → stackRoom=0
            gold=800, price=200 → afford=4
            return min(4, 0) = 0
       Clamp(1, 0) → 写回 TMP/DigitStrip = 0
```

决定路径上也曾打出过「持有 10 + 购买 11 > 10 整单取消」——说明背包满堆叠在现网 Play 会话里**反复出现**，与「输入皆 0」同一根因族。

## ⑤ 最小修方向（交施工员）

纪律：禁止关 `ResolveBuyMaxQuantity`；禁止改价表交差。

| 优先级 | 做法 |
|--------|------|
| **必做** | 保留 `[ShopBuyMax]`（或开关）；验收贴 `gold≈800 … stackRoom>0 … max≥1` |
| **G2 产品** | 堆叠满时：输入钳 0 **可保留**，但须可辨——Console 已有；建议决定/输入侧叠加「堆叠已满」提示（对白/Tips 另定），避免玩家以为「有钱却坏了」 |
| **验收前置** | 复验档先确认 `HpBall` held&lt;10（用掉/调试 Set 数量）；满堆叠时「变 0」属预期业务，不算本 bug 未修 |
| **若 held&lt;10 仍 max=0** | 再查 G1/G4/C1（届时以新 `[ShopBuyMax]` 为准） |

### 方案对比

| 方案 | 做法 | 裁决 |
|------|------|------|
| **A** | 证 G2 + 日志可辨 + 有空位时保证 1～4 可输；满堆叠提示 | **主推** |
| **B** | 关购买联合钳制让任意数能输 | **否决** |
| **C** | 满堆叠时抬高 MaxStack / 绕过 stackRoom | **否决**（破坏堆叠硬顶） |
| **D** | 只再改清空时序 | **否决**（上轮已做，验收失败） |
