## 一、今日修复总结

### 1. `FightingFormLogic`：战斗立绘「闪烁」的修复原理

- **现象**：整段故事结束（`OnStoryEnd`）后，若**立刻**把战斗立绘切回显示，容易与**仍占屏/正在切换的下一层对话 UI** 发生在同一短窗口内，出现「露一帧再被关掉」的感知，即**战斗立绘闪烁**。

- **做法**：在「剧情刚结束、需要**恢复**战斗立绘」的路径上，**不立即** `SetActive` / 可见性，而是走协程 **`CoApplyBattleImageShowAfterStoryEnd`**，先 `WaitForSecondsRealtime` 等待配置时长（字段 **`_storyEndBattleImageDelay`**，约 **0.3～0.5s** 可配，默认约 **0.4s**），再调用 **`ApplyBattleImageShowNow`**。

- **原理**：用时间窗把「故事收尾 UI」与「战斗 HUD 再出现」**错开**，避免与 `StoryComponentGSM` 流程、下一段 `OnStoryPrefabLoad` 里**先关战斗立绘**等操作**抢同一帧**。

- **维护提示**：该延迟与**取消协程**（如界面隐藏/切场景时 `StopCoroutine`）是配套设计；**勿随意改为 0 或删掉协程**，否则易回归「剧情衔接处立绘闪烁」。

### 2. 摄像机：从动画控制改为代码平滑跟随

- **方向**：机位/回跟玩家不再依赖在 Timeline 或 Animator 里「拖轨道硬播位移」，而由 **代码** 驱动（与现有 **Cinemachine** 体系配合）。

- **要点**（以 `CameraComponent` / 相关跟随逻辑为准）：

  - 使用 **`Vector3.SmoothDamp`** 做**平滑对齐**；`SetFollow` 在 **`forceSnapToTarget==true`** 时从当前机位向「目标 + 偏移」靠拢，**`smoothTime`** 控制过渡快慢（**0 则保持近似瞬切**语义）。

  - **FixedUpdate 与抽动**：`SmoothDamp` 的 `delta` 使用 **`Time.fixedDeltaTime`**，与 **Rigidbody2D** 同相位；`CinemachineBrain` 可配置为 **`m_UpdateMethod` / `m_BlendUpdateMethod` → FixedUpdate**（`syncCinemachineBrainToPhysicsStep`），减轻 **Update/LateUpdate 与物理步错位**带来的**末端对位「抽动」**。

  - **架构旁注**：`PlayerOffsetCameraFollow` 等脚本同样强调 **SmoothDamp 与 `fixedDeltaTime` 一致**，主摄像机/机位空物体**不再**挂在旧「CameraTrack 带飞」路径下，由统一跟随逻辑接棒。

- **与剧情线的衔接**：`ForestSceneLinEnStory` 等仍可能用**协程**在固定时长内**线性插值** `cameraTrack` 位置，结束时调用 **`AnimaEventTrigger("CameraMoveEnd:")`** 与 **`OnCameraMoveEnd()`**；这部分与**纯 vcam 平滑**并存时，以场景实际挂载为准，明日重点统一「**机位平移**何时算完、**谁**发完成信号**。

## 二、当前逻辑链路图（文字版）

**当前可描述的主干如下：**

1. **对话/剧情节点**：`ForestSceneLinEnStory` 对话图执行到 **`OnDialogueEnd()`**（NodeCanvas `ExecuteFunction`），用于收尾对话、解锁镜头、起 BGM/SFX 等，并**启动**与镜头相关的协程或状态。

2. **摄像机平滑/平移**：
   - 一侧是 **`CameraComponentGSM` + `CameraComponent`** 的 **SmoothDamp 回跟**、**Cinemachine** 的 Follow/状态对齐；
   - 另一侧（林恩线）可能是 **`CoMoveCameraTrackToPlayerOverTime`**：在 `cameraTrack` 上按 **`cameraMoveToPlayerDuration` 做插值，结束后再** `TryNotifyNodeCanvasCameraMoveEndEvent()`**（事件名 **`CameraMoveEnd`**）并调用 **`OnCameraMoveEnd()`**。

3. **断点（今日「卡」的位置）**：

   - **Dialogue End →（镜头协程/平滑跟拍 进行中）→ `CameraMoveEnd` 被监听 → 对话图继续** 这一段，在工程里**依赖** `AnimationEventRegisterTaskAction` 与 `AnimationEventComponent` 的**注册/触发时序**。

   - **更下游**：期望在「**机位平移/回跟**真正结束」后，**稳态触发**下一段**动画、教学或对话**。目前缺少一条**在所有人心中一致**的「**抵达 / 完成**」契约（见明日待办），故链路在脑子里往往写成：

   **`Dialogue End → Camera Smooth Move → ???`**

   其中 **`???`** 即：**谁、在何时、以何种回调或事件，驱动「下一段内容」**。

## 三、明日待办（棘手问题）

### 核心目标

- **在摄像机平移/平滑回跟**完成后，**可预期、可复现**地触发**下一段过场动画、教学引导或下一段 NodeCanvas 对话**。

### 技术猜想与排查顺序（建议）

1. **「抵达」信号是否成对**

   - 若剧情依赖 **`CameraMoveEnd`**：用现有 **`debugLogCameraMoveEndFlow`（如 `ForestSceneLinEnStory`）** 对照控制台，确认 **`RegisterEvent` 先于 `AnimaEventTrigger`**、且组件引用为**同一块** `AnimationEventComponent`。
   - 若使用 **`CameraComponent.SetFollow(..., onComplete: ...)`**：核对 **`onComplete` 是否必达**、是否与 **SmoothDamp 收尾**的 `FixedUpdate` 路径一致（双通道时不要漏绑）。

2. **是否缺「机位平移完成」的单一真源（Single Source of Truth）**

   - 可能同时存在：**协程时间结束**、**vcam 位置逼近阈值**、**Timeline/Signal** 多路；需收敛为**一条**对外回调或**一个** UnityEvent/Signal，再驱动教学/对话。

3. **插件与节点图**

   - **NodeCanvas**：「等待事件 → `ExecuteFunction` `OnCameraMoveEnd`」与 **协程里直接 `OnCameraMoveEnd()`** 可能各跑一次；确认 **双调是否幂等**、**下一步 `TriggerStory` 是否**在**对话树未被 `SetActive(false)` 误伤**的对象上跑（参见此前讨论：关的是 **3D 逻辑体** 还是 **UI 对话宿主**）。

4. **可交付的最小验收集**

   - 在「平移完成」帧打**一条** `Debug.Log`（含 `Time.frameCount` + 完成原因枚举），与下一段教学入口日志做**成对**出现即视为打通。
