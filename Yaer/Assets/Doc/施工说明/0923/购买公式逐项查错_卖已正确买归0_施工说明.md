## 沟通摘要

### ① 结论一句话

**买提交归 0 是因为该道具堆叠已满（空位 0），不是金币/单价算错；公式不改。验收前先腾出背包空位。**

### ② 原因（通俗）

钱够买 4 个，但生命球已经 10/10 装满，商店不允许再买进，提交后就把数量收成 0。卖之所以「正常」，是因为卖只看持有、不看「还能再塞多少」。

### ③ 用户检查清单

| # | 步骤 | 期望 |
|---|------|------|
| 0 | **前置**：背包生命球 held&lt;10（用掉或调试减数量） | 否则满堆叠归 0 属预期 |
| 1 | 菜单金 ~800；Commit 看日志 | `[ShopBuyMax] … held&lt;10 stackRoom≥1 afford≥1 max≥1` |
| 2 | 买输入 1/2 再提交 | **留下**该数（≤max） |
| 3 | held=10 再提交 | 归 0 + Console「该道具已满」；**不算 bug** |
| 4 | 卖 | 仍完全正确（本票未改卖） |

### ④ 程序补充

| 路径 | 改动 |
|------|------|
| `ShopFormLogic.cs` | **算术未改**；`[ShopBuyMax]` 增打 `afford=`；注释钉死 F1-(b) 设计门 |
| 卖端 / 编辑锁时序 | **未改** |

**产品策略（施工默认 = 报告 F1-(b)）**

- 满堆叠提交→0 + 已有「该道具已满」Console = 预期  
- 禁止关 `stackRoom` / 抬 `MaxStack` / 改读金「交差」  
- Tips 图集键另票；现网 Console 可辨即可  

**本档证据原文**：`gold=800 price=200 held=10 stackRoom=0 otherCost=0 max=0` → `min(4,0)=0`。
